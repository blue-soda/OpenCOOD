## 1. 本次回答的问题

共享位置是 `backbone_3d.conv_out` 最后一个 Multispike 之后、HeightCompression 之前。
每帧特征为 `[M,128]`，值域实测为 `{0,1,2,3,4}`；稀疏地址为 `[M,3]` 的 z/y/x。
原张量仍是 float32。本次首次实际序列化这些计数并解包，再接回原检测器。

两种无损格式使用相同 uint16 z/y/x 地址：

1. `dense3`：保留位置的每个通道固定 3 bit。
2. `mask3`：每个位置带通道非零位图，仅将非零计数以 3 bit 保存。

编码前去掉全零向量，按两种格式的实际长度选择较短者。
包内计入 20 字节格式头、实际 UTF-8 JSON 元数据、地址、位图/计数及 4 字节 CRC32。
元数据包含帧 ID、层名、模型哈希和网格形状。
**这是特征包大小，不是完整网络线上流量**：未加入真实位姿/时间戳、分片、重传、传输层开销。
当前地址只是发送端 sparse tensor 索引，尚未建立跨车物理坐标契约。

## 3. 无损与耗时验证

初版和优化版分别完成 64 帧检查，每帧均满足：

- 解包地址、非零计数与编码前逐项相同。
- 全零向量被剔除后，恢复的完整稠密特征与原张量 `torch.equal`。
- 分类、回归、方向三个头的输出，以及后处理后的框和分数，逐项精确相同。

本地与服务器的 codec 测试还覆盖空输入、全零输入、非 8 整除通道数、最大 uint16 地址、
非法值、重复地址、数据损坏与截断。均通过。

首版对两种候选都实际打包，CPU 成本较高。优化改为先计算长度选择格式，并保持位操作为 uint8，
避免构造最终不用的稠密载荷和较大的 int64 临时数组。

**成对 CPU 基准**：冻结真实帧 000211 的同一组数组，3 次预热，40 次/方法，交替先后顺序。
两种方法每次输出均与已保存的 128,189 字节原包完全一致。

| 方法 | 编码中位数 | 编码 P95 | 解码中位数 |
| --- | ---: | ---: | ---: |
| 初版 | 26.75 ms | 39.31 ms | 9.30 ms |
| 优化版 | 10.65 ms | 20.38 ms | 9.24 ms |

64 帧优化版审计中的编码中位数/P95 为 18.86/33.82 ms，解码为 12.63/22.26 ms。
不同帧大小及共享服务器负载影响耗时，不能拿两个独立运行的耗时直接解释优化倍率。
上述计时只包含 CPU 数组编码/解码，不含 GPU 拷贝、实际网络、融合或完整检测。

**重复性边界**：两个独立 GPU 回放的计数直方图出现极小差异，64 帧总包大小相差 66 字节，
非零向量数相差 3。没有把跨运行的特征声称为 bitwise deterministic。
每次运行内部的 codec→检测器回放仍全部精确相等；冻结同一组特征时，优化前后包字节也完全一致。

## 4. 当前结论与下一步

已验证：原生 Count4 共享层能直接成为可寻址、可无损打包的消息，不需要先学习另一个编码器。
但这尚不能证明优于低比特 ANN、实现协作增益或降低端到端能耗。

继续顺序：

1. 完成当前 SNN/同结构 ANN 各 60 轮训练，按完整验证 AP50 冻结最佳权重，并重放最终指标。
2. 明确空间契约，再做跨车几何单元检查：3D 主干三次 stride=2 后，conv_out 额外在 z 方向 stride=2，
   因此总 stride_zyx 为 **[16,8,8]**；既有 `spike_stride=8` 只能按 BEV/xy 理解。
   需同时推导 padding 导致的坐标中心偏移，纳入真实位姿、时间戳与有效性掩码；本次 packet 尚未用于 SE(3) 对齐。
3. 用相同共享层、检测头、样本和空间选择比较原生计数与 ANN INT2/4/8，按实际字节预算评估 AP。
4. 几何和信息有效性通过后，再实施两端同步融合；最后才引入到达驱动状态、丢包和截止时间。

当前未新增协同模型长训练。已有 `e3dsnn` heartbeat 继续跟进两条单端训练，后续最终权重再次运行该审计。

## 6. 进一步无损压缩：字节核算与保存包探针

用户询问的 93.24% 零元素比例与平均 155.30 KB 确实来自同一 conv_out 特征。
零比例的分母是活跃稀疏位置的 M×128 个通道元素，不是整个通道是否失效，也不是全零位置比例。
155.30 KB 已利用全零位置剔除和非零通道掩码，不能再乘一次 6.76% 估算压缩后大小。

基于优化版 64 帧逐帧记录，平均包拆分如下（十进制 KB）：

| 组成 | 平均字节 | KB |
| --- | ---: | ---: |
| uint16 z/y/x 地址 | 36,217.03125 | 36.22 |
| 通道非零位图 | 96,578.75 | 96.58 |
| 非零计数，当前每值 3 bit | 22,230.796875 | 22.23 |
| 格式头、JSON 元数据和 CRC | 276 | 0.276 |

当前编码仍不是最紧凑表示。以下是按实际 M、非零元素数及逐帧字节对齐计算的**布局估算**，未实现新协议或运行其检测回放：

| 累积优化 | 预计平均包 |
| --- | ---: |
| 非零值仅有 1/2/3/4，编码 q−1 为 2 bit；零由掩码表达 | 147.89 KB |
| 再将 z/y/x 展平为索引；18,900 格可用 uint16，地址从每位置 6 B 降至 2 B | 123.75 KB |
| 改用整个 18,900 格的占用位图（2,363 B），按位置顺序排列保留特征 | 114.04 KB |

这些估算保留当前包头大小，不包括新协议额外字段或完整传输开销；采用具体版本时仍须验证解码与排序一致性。
计数 0..4 的无条件固定长度编码仍需 3 bit；利用非零掩码后的条件值域只有四种，因此可无损使用 2 bit。

另对保存的真实首帧 000211 做了 zlib 无损压缩探针：原包 128,189 B（不是 155.30 KB 平均包），
每档预热 3 次、重复 30 次，逐次验证解压字节完全相同。

| zlib 等级 | 压缩后字节 | CPU 压缩中位数 | CPU 解压中位数 |
| --- | ---: | ---: | ---: |
| 1 | 63,487 | 3.63 ms | 0.95 ms |
| 3 | 60,537 | 6.57 ms | 0.84 ms |
| 6 | 56,832 | 18.86 ms | 0.84 ms |
| 9 | 54,910 | 138.91 ms | 0.80 ms |

这是 CPU 内存驻留的单帧测量，耗时是额外压缩/解压步骤，不包含原 codec、GPU 拷贝或网络。
不同等级顺序测试，没有按方法交替，不能视为严格性能排序；仅作为压缩空间及耗时量级探针。
未把单帧的 63.49 KB 声称为整个验证集平均值，也未修改当前默认 codec。
zlib 字节数包含其压缩流本身，不含额外传输封装。

下一步优先比较上述无损格式的真实字节与额外耗时；空间选择、通道剪除、降维等有损方案则需完整 AP–字节实验。
证据：`results/packet_compression_probe_20260929.json`，同步用户指定 evidence 目录。
